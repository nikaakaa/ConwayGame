# 生命游戏核心性能记录

## 条件与可用结论

2026-10-17，Unity 6000.3.3f1，Entities 1.4.8、Burst 1.8.29、Collections 2.6.8；i9-13900HX，24 核、32 线程。早期采样前整机 CPU 负载约 54%，另有项目与 Editor 负载，该读数不代表后续各轮负载。以下记录目标 Editor 内正式核心的绝对耗时与输出，旧核心未获得有效同输入基线。

独立核心采样通过官方 Unity CLI 的 `eval_file` 创建 World，调用 `LifeWorld`、`LifeSimulationSystem` 与 `LifeRasterJob`。Stopwatch 只包住实际操作，CLI 分发、动态编译、输入准备与初始建树另记。每个版本测量五次冷请求及其热重放，冷、热交替；不同版本顺序采样，没有交替安排版本，不报告精确加速倍数。连续八宏步面对同一次运行中的不同状态，不算八次重复测量。真实 Play 的被动观测单独记录。

多次检查发现目标 Editor 的 Profiler 历史录制开启，并出现内存压力与丢弃历史帧警告。耗时保留为各次 Editor 条件下的诊断和输出证据，不作为纯游戏性能上限。每次关闭历史后的真实 Play 单独注明；仅先前关过录制，不能证明随后重进 Play 的采样仍关闭。不同演化状态不能作精确性能对照。

批量建树前的数据在 [core.json](../../Tools/Benchmarks/Results/core.json)、[metapixel.json](../../Tools/Benchmarks/Results/metapixel.json)、[galaxy.json](../../Tools/Benchmarks/Results/galaxy.json) 与 [scheduler.json](../../Tools/Benchmarks/Results/scheduler.json)，当时的源码和样本哈希见 [source-hashes.json](../../Tools/Benchmarks/Results/source-hashes.json)。这些哈希不代表后续的批量建树和回收优化版本。

分配指标需要更正：本机 `GC.GetAllocatedBytesForCurrentThread()` 对保留的一份 `new byte[1048576]` 前后都返回 0。历史 JSON 保留原始字段，但其中的 `allocatedBytes: 0` 不能证明无分配，不影响单独记录的 Stopwatch 耗时与输出核对。当前工具改用 Unity `GC.Alloc` 的主线程事件计数，并在每轮脚本先执行已知分配和空区间校准。事件样本的 `Value` 是时间指标，不作字节数；缓冲截断时分配结果无效。

独立参考的调用方式也已纠正：`copy/life` 的普通结果缓存不包含步长，必须通过 `set_step` 改变步长以清理旧缓存。旧包装直接写 `life.step`，在显示器上给出了错误参考。改用正式方法后，第 22,071 和 22,583 代的完整坐标指纹均与核心一致，见 [hex-reference.json](../../Tools/Benchmarks/Results/hex-reference.json)。另重新计算银河初态及八个宏步，九个检查点与原参考全部一致，见 [galaxy-reference-correct-step.json](../../Tools/Benchmarks/Results/galaxy-reference-correct-step.json)；其它旧输入未因这次修复而自动获得重新验证。

## 最大巨构的加载与首次推进

2026-10-18，运行核心为 `b174a4f`，包含 `4b880fb` 的地图数据所有权、`5d8966f` 的区域网格原点和 `75ba16f` 的 RLE 中间内存修改。输入是库中最大的 `metaglider-0e0p.rle.gz`，完整初态为 **93,235,805 活细胞、23,025,060 个 16×16 叶块**。世界仍完整载入内存，没有磁盘分块流式加载；视野按需求值与周边预加载继续使用原正式路径。输入、源码与采样口径见 [giant-source-hashes.json](../../Tools/Benchmarks/Results/giant-source-hashes.json)。

地图经 `LifeWorldStore.LoadAsync` 解析后直接交给 `LifeSession.LoadWorld` 建树，不再作为画笔库的字典键长期保留托管叶块数组。RLE 首次扫描负责协议校验和边界，第二次扫描直接按最终中心坐标打包，删除整段 `Trim` 复制及第二份巨型重居中字典。一次完整载入记录解析 **85.365 秒**、建树 **6.505 秒**；解析结束的托管已用读数为 3,742,670,848 字节，进入棋盘后为 903,266,304 字节，初态共享节点 725,632。见 [giant-full-load.json](../../Tools/Benchmarks/Results/giant-full-load.json)。这些是阶段读数，不是峰值或整个进程占用；这轮解析仍有一分钟以上等待。

旧的区域查询固定按世界零点划分网格，而完整图案初始树的根有自己的坐标原点；查询会把可共享的树拆成大量位置条目。现在每个编辑 Epoch 保存并继承初始树网格原点，视野、因果依赖与父子区域查询全部按该网格对齐。在同一份 1,048,382 字节前缀输入上，旧路径达到明确设置的 200,000 区域条目上限仍未完成；新路径以 **32 个区域条目完成一代**。旧版和新版分别消耗 363.538 ms、208.026 ms 的 Pump CPU，但旧版没有完成，不能据此计算加速倍数；两轮还包含不同的 Editor 等待。见 [修改前](../../Tools/Benchmarks/Results/giant-region-before-batched.json)与[修改后](../../Tools/Benchmarks/Results/giant-region-after-grid.json)。这份有界输入只用于定位查询问题，不代替完整地图结果。

巨构远景还存在冷缓存首次请求过大的问题。视野 1,048,576 格、目标 1280 代/秒时，旧策略直接请求 1024 代；[30 秒记录](../../Tools/Benchmarks/Results/life-frames-giant-grid.json)中发布代数始终为 0，缓存由约 43 万增至 269 万。现在视野与速度只决定跨度上限，首次请求从一代开始，每次完成后逐级增加；相对最近编辑的时间基底对齐，发布代数依次到 1、2、4、8……。编辑重置预热，暂停保留预热结果，不改变实际生命规则。

重进 Play 创建新世界、从正式解析结果重建完整初态后，缓存条目为 0，视野固定在 `(-524288, -524288)`、边长 1,048,576 格。最终 [30 秒记录](../../Tools/Benchmarks/Results/life-frames-giant-warmup-full.json)共 3321 帧，从第 0 代发布到第 1 代；第一次代数变化约出现在记录累计 23 秒处。帧间隔中位数 / P99 / 最大为 **8.972 / 11.485 / 153.179 ms**，模拟单帧最大 **147.705 ms**，仍有冷求值及大容量容器扩容期间的停顿，不能承诺稳定 60 FPS。随后现场全景读数已发布第 16 代，见 [运行内存快照](../../Tools/Benchmarks/Results/giant-runtime-memory.json)。这些顺序单次诊断不构成精确加速对照，也不能把目标代速当成实际吞吐。

同一完整世界从第 4 代开始执行正式 `OnPointerMove / OnDrag / OnScroll` 的五轮、540 帧[全景回放](../../Tools/Benchmarks/Results/interaction-giant-full.json)，在 524288～1048576 格视野切换。外部相机变化、命中失败、输入前后纹理覆盖缺口均为 0；拖动帧间隔中位数 / P99 / 最大为 **9.655 / 11.273 / 11.930 ms**，缩放为 **8.967 / 10.868 / 11.039 ms**。该回放期间下一步演化仍在途，发布代数保持第 4 代；它证明相机交互能持续处理，不能证明下一代已经算完，也不测 GPU 完成或物理鼠标到像素延迟。棋盘栅格计时全为零，表示这段没有完成新的棋盘栅格更新，不表示巨构重绘没有成本。

另有 [65536 格运行记录](../../Tools/Benchmarks/Results/life-frames-giant-warmup-running.json)在 30 秒内由第 4 代到第 16 代，以及[较近视野交互记录](../../Tools/Benchmarks/Results/interaction-giant-warmup.json)。它们的视野与旧全景基线不同，单独保留，不作为全景加速证据。原有 [413 项独立区域对照](../../Tools/Benchmarks/Results/giant-viewport-check.json)重跑失败 0，脚本 1.378 秒；未新增或修改 Unity 测试代码。

内存仍有明确限制：第 16 代快照的原生容器数据容量约 **1.04 GiB**，不含分配器元数据、纹理和其它 Unity 资源；尚未加入缓存字节硬上限或原生容器容量回缩。Mono 的 `Process.PrivateMemorySize64` 在本机返回 0，该字段无效。Editor 的托管堆预留仍保留旧解析产生的约 18.9 GB 高水位，系统进程私有提交约 30.3 GB，不能把 0.90 GB 托管已用值说成进程仅占 0.90 GB。新进程的峰值和完整巨构长跑内存上限尚未测得。

## 当前视野按需版本

2026-10-18，已测核心对应 `7a43787`：视野只请求其反向因果依赖，保存/复制固定版本后准确结算，`POP~` 显示已有历史样本，不为统计主动计算全图。近景与全景的工作范围不同，不以二者耗时之比表示加速比。以下原始结果保存在 `Tools/Benchmarks/Results/`，工作输入保存在忽略的 `Tools/Benchmarks/Work/`，不依赖 Unity 退出时会清理的 Temp。版本、输入与证据校验和见 [viewport-source-hashes.json](../../Tools/Benchmarks/Results/viewport-source-hashes.json)，其中区分已测核心、静态显示修改和捕获时 UI，不把事后捕获的哈希当作所有历史测量的源码证明。

`PrepareLifeViewport.cjs` 使用固定 SHA256 的原始 `copy/life`，通过正式 `set_step` 推进。三组输入包含离屏滑翔机进入视野、同代覆盖与跨代编辑、相距百万格及千万格的稀疏重复结构；独立参考保留完整坐标，并以逐代推进核对混合跨度参考。正式核心分别按每检查点导出、延迟导出、保留旧导出三种顺序运行，核对区域人口、坐标双指纹和快照代数。

最终 [viewport-current.json](../../Tools/Benchmarks/Results/viewport-current.json) 共 413 条检查、失败 0，脚本总耗时 0.140 秒；[独立参考](../../Tools/Benchmarks/Results/viewport-reference.json) 保留完整坐标及区域指纹。这是小场景正确性和任务完成证据，不是 Game 帧率。

15 次完整导出均为 3,388,590 活细胞，和指纹 `635988e27ba1c37e`、异或 `da3d99da0f38ecfc` 均匹配独立第 22,583 代；视野输出也与导出裁剪一致，失败 0。全部 15 个视野推进及其已有回收尾部区间记录 0 个主线程 `GC.Alloc` 事件，已知分配和空区间校准通过、4096 条缓冲未截断，Profiler 历史关闭。该口径排除初始化、导出、绘图和 UI，不能表示整个游戏 0 GC。

长跑诊断使用同一输入、4096 格视野，连续 512 次 32 代请求，完成 16,384 代。停用回收只用于定位重复冷算；正式回收和停用回收各运行一个新世界。两者最终导出排序后逐坐标一致，均为 3,394,840 活细胞；缓存命中均为 8,953,831，未命中均为 893,019，失败 0。正式回收推进 CPU 为 2990.748 ms，2249 个回收批次，结束时 861,352 节点、11,545 区域条目；停用回收为 3030.413 ms。此单次顺序诊断只证明回收没有导致该输入重复丢失工作集，不用两项接近的数值宣称加速。正式回收最慢一次请求仍需 605.709 ms CPU，且保留工作集增加内存；没有测量该长跑的 GC.Alloc。详见 [viewport-long.json](../../Tools/Benchmarks/Results/viewport-long.json)。

完整银河仍为真实 15×15 OTCA 电路、初态 7,408,195 活细胞、556,344 叶块。最终版本从初态完成 35,328 代的一次冷请求：视野推进 1403.874 ms、准确全图导出 269.699 ms，合计 1673.573 ms；解析 5841.441 ms、建树 117.744 ms 均不计入推进。最终人口 7,070,723，指纹和 `f2c01c6befc06876`、异或 `147baceed955b16a` 与独立引擎一致，失败 0。随后重放相同初态、相同请求的视野 CPU 为 62.425 ms，其中约 59.948 ms 为回收；它不能表示下一宏代的吞吐。这里只重跑一组冷/热请求，没有把历史八宏步计入本版本。冷请求最大 Pump 批次 13.365 ms，回收批次最大 1.148 ms。详见 [viewport-galaxy.json](../../Tools/Benchmarks/Results/viewport-galaxy.json)。

正式 `LifeSimulationSystem` 以合成时间五次完成同一显示器后续 512 代，窗口 65536 格、策略跨度 512 代；视野 CPU 中位数 764.375 ms，范围 593.794–815.354 ms，最大单次 Update 为 10.502 ms。推进与回收同时在途时提交 64 格画笔，消费耗时中位数 0.749 ms，范围 0.725–2.571 ms，用 1–2 次 Update 完成；全图导出核对五次均准确增加 64 格。推进和编辑共失败 0，首个推进区间有 1 个初始化分配事件，其余推进与全部画笔区间为 0。没有真实帧等待、绘图或 UI，不能把命令消费耗时当成鼠标到显示延迟。详见 [viewport-system.json](../../Tools/Benchmarks/Results/viewport-system.json)。

已确认的成本来源分别是：大片空白未按完整来源链剔除；原生 HashMap 计数遍历回收空闲链；区域时间切分依赖最近结果而制造重复检查点；回收只强留输出，删掉仍有复用价值的重叠输入。当前路径分别采用因果活源查询、所有者维护条目计数、二进制时间边界，以及清扫前保留最近两轮演化缓存输入。具体职责见[核心设计](../路径/混合演化核心设计.md)。

`retained-export` 的视野阶段会同时推进已排队导出，因此该模式的 `viewMs` 包含部分导出工作，`exportMs` 只记剩余等待，二者不能解释成互不重叠的两项独立成本。`maxPumpMs` 仅记录 Pump；新增加的 `maxBatchMs` 才包含同批回收。大图另记录视野发布后及导出后的已有回收尾部，分配观测覆盖视野维护尾部。只在已知分配和空区间校准通过、事件缓冲有效且未截断时解释分配计数。

工具静态审查后补齐了含 `int2` 元组的标量序列化，并把 `MeasureLife`/`MeasureLifeInLife` 的缓存计数读取移至推进结束、导出之前；这些整理尚未全部重跑。既有 `viewport-galaxy.json` 的缓存计数仍包含导出访问，原始字段保持不变，不据其计算推进阶段命中率。帧工具新增 `overlayRasterMs`，单独记录覆盖层，样本不足两帧时标记无效。新显示链路已经重编译并实际采样，交互证据见下文。

当前预算是批次边界的软期限。来源树遍历、原生扩容、列表批量收尾和导出数组生成仍有同步段；跨代编辑保留必要来源历史，完整保存不会自动压缩历史链。不能据以上核心采样承诺 60 FPS、均匀发布或无停顿。下列旧采样属于此前整图推进实现。

### 拖拽、缩放与预览

2026-10-18 已在用户授权保存、恢复棋盘后重编译并实际回放，已测第一阶段运行时为 `b417403`，原始资料见 [interaction-summary.json](../../Tools/Benchmarks/Results/interaction-summary.json) 与 [源码、输入和样本清单](../../Tools/Benchmarks/Results/interaction-source-hashes.json)。原先只有一帧的 [被动记录](../../Tools/Benchmarks/Results/life-frames-interaction-before.json) 仍是无效帧率样本，不能作为前后对照。

定位到的正式链路是：鼠标预览和窗口变化会使整张棋盘失效；区域请求不断被新窗口取消；即使拆开覆盖层，CPU 仍在一帧内生成完整棋盘像素。第一次即时相机版本的 [540 帧记录](../../Tools/Benchmarks/Results/interaction-after.json) 中，棋盘绘制峰值 19.888 ms，拖拽 `LateUpdate` 峰值 24.454 ms，因此没有把这次中间修改判为完成。

第一阶段改为即时相机与完成纹理范围分离，输入、预览和选区使用同一相机，GPU 重投影已有图片；区域请求完成在途窗口再接续最新窗口。棋盘按约 1 ms 软预算分帧生成，固定树通过正式节点回收根保留，完成后才交换纹理。中键缩放同步更新拖动基准。

将同一存档的 6,435,151 个细胞恢复为第 0 代，视野 32768 格、目标 1280 代/秒。每轮 12 帧空闲、24 帧预览、48 帧拖动、24 帧缩放，重复五轮，共 540 帧。工具调用正式鼠标入口，临时开启后台运行、关闭 Profiler 历史，结束恢复。下表是各区间的绝对结果；暂停与播放、旧时间基底与恢复后的新基底不能计算精确加速倍数。

### 周边预加载与远景跨度

最终显示实现为 `4728ac4`，远景调度为 `b6ee03c`。HashLife 区域求值仍然使用跨代缓存；原先每秒至少发布 15 次的限制，让目标 1280 代/秒、131072 格视野的请求止于 64 代，现在放宽为每秒至少一次的速度上限，同一设置允许 1024 代。约一秒只描述信用积累，不保证求值完成期限。缩放改变请求跨度，目标代数每秒仍由速度设置决定。

即时相机派生四分之一屏对齐、3.5 倍边长的预加载范围，步长继续读取真实相机。两份 3584² 棋盘纹理保持每屏 1024² 的纹素密度，连同覆盖层的 CPU 像素共 102 MiB，GPU 存储另计。缓存为有限范围，连续多档缩小、远距离移动或首次冷加载仍可能超出已有图像。

## 批量建树与连续 Life-in-Life

`LifeWorld.BuildShape` 已改为 Burst 中按 Morton 顺序排序叶块，自底向上拼树。相同完整银河的五次建树耗时为 **65.486–150.044 ms，中位数 73.145 ms**；第一次解析单次 3362.125 ms。五次从初态推进 35,328 代的 CPU 耗时为 3794.224–4421.635 ms，中位数 4020.872 ms；十次冷／热输出均与独立指纹一致，失败 0。数据见 [galaxy-bulk-build.json](../../Tools/Benchmarks/Results/galaxy-bulk-build.json)。

## 回收停顿与当前对照

## 显示器的更新停顿

用户指出界面和缩放可动、棋盘更新停顿，并确认地图为 `hexadecimal.rle`（显示器）。原调度直接把累积待推进量组合为大请求，每帧只给约 2 ms，整次请求完成后才发布世界。[现场记录](../../Tools/Benchmarks/Results/life-frames-current-stutter.json)为 20 秒、2078 帧，全程运行、目标 20,480 代每秒，第 22,071–26,167 代只有 11 次代数变化，观察到的请求结果相隔 256 或 512 代。最长同代区间约 **2679.48 ms、275 帧**；System 最大 2.1117 ms，说明主线程可持续更新时，世界仍可能长期没有可发布的新结果。

该阶段的 `LifeSimulationSystem` 将自动请求初始上限设为 32 代，按每次推进跨帧累计的实际处理时间调节后续步长；完成自动请求后继续利用本帧余量，单帧模拟软预算由 2 ms 调为 8 ms，回收占约四分之一。33.3 ms 的调节目标是推进处理时间，不能解释为固定墙钟延迟。显式单步仍为一代，画笔仍取消尚未发布的自动推进并编辑当前世界。当前策略已替换为视野跨度与整帧反馈预算，见[核心设计](../路径/混合演化核心设计.md)。

正式 System 从同一快照重复五次，初始时间 0.025 秒、目标 20,480 代每秒，随后零时间续跑，均完成 512 代且匹配独立指纹，失败 0。CPU 中位数 **412.938 ms**，范围 **393.194–509.395 ms**；首次发布中位数 **32.220 ms**，范围 **32.166–40.559 ms**；每轮记录 9–11 次代数变化。所有更新中最慢一次 **10.1209 ms**，说明 8 ms 仍是批次边界上的软预算。这不是实际 Game 帧率测量，见 [hex-scheduler-cadence.json](../../Tools/Benchmarks/Results/hex-scheduler-cadence.json)。

随后在推进和回收均进行时提交 64 格画笔，五次都在一次更新内消费，CPU 中位数 **2.255 ms**，范围 **2.225–7.763 ms**；回收完成后，整个世界符合原结果加 64 格的预期。经校准的主线程 `GC.Alloc` 计数在首轮推进和画笔分别为 1、3 个事件，后四轮对应区间均为 0。初始化不能合并宣称无分配，结果不包含鼠标到显示的延迟。

重新从已核对的第 22,071 代准备真实 Play，目标速度仍为 20,480。预热和启动采样后，[新记录](../../Tools/Benchmarks/Results/life-frames-hex-cadence-live.json)覆盖第 **23,564–31,708 代**，20 秒、1019 帧全程运行，Profiler 历史在采样开始和结束均关闭。共 **155 次代数变化**，观察到的跨度为 16、32、64、128 代。按同代样本归组并累计各样本的帧间隔，中位数约 **113.67 ms**、P99 **392.70 ms**，最长 **405.16 ms、22 帧**；该口径包含每组首样本之前的一段帧间隔，并非精确发布延迟。最长组首末样本之间实际为 378.66 ms。末态人口 **3,122,350** 与独立第 31,708 代相同；该 Play 末态只核对人口，未遍历整个世界指纹。

新记录 System 最大 8.5332 ms；Editor 帧间隔中位数 18.146 ms、P99 31.6523 ms、最大 40.5179 ms。增加模拟预算会占用更多主线程，两份 Play 的演化区间、缓存与同期 UI 状态不同，不作为受控加速或帧率对照。现场旧状态没有保存完整快照，固定初态的步长对照由 RLE 重建；新调度仍有约 0.1–0.4 秒的可见更新间隔，不能宣称流畅逐帧播放或全部停顿消除。汇总定义和复算结果见 [hex-cadence-summary.json](../../Tools/Benchmarks/Results/hex-cadence-summary.json)，核心与工具来源见 [hex-cadence-source-hashes.json](../../Tools/Benchmarks/Results/hex-cadence-source-hashes.json)。临时后台运行设置已恢复为 false。

## 空闲帧异常修复

迁移初版在空队列时调用 `DynamicBuffer.RemoveRange(0, 0)`。Entities 1.4.8 先检查起始索引，再处理零数量，所以每次空闲更新均越界。原画笔采样只覆盖有命令的路径，未发现该问题。

已在目标 Editor 复现原异常，改为仅移除本次实际消费的命令前缀。重新编译为 0 错误、0 警告；正式 System 在空队列下更新 360 次、运行状态下更新 120 次，连续画笔得到预期的 33 格，单步得到第 1 代，运行后得到第 121 代，暂停后队列长度为 0。此次通过 CLI 直接检查，未新增 Unity 测试代码。`core.json` 和单 OTCA 采样产生于该修复之前，完整 Galaxy 和正式调度采样产生于修复之后。
