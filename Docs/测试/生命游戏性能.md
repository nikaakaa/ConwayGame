# 生命游戏核心性能记录

## 条件与可用结论

2026-10-17，Unity 6000.3.3f1，Entities 1.4.8、Burst 1.8.29、Collections 2.6.8；i9-13900HX，24 核、32 线程。早期采样前整机 CPU 负载约 54%，另有项目与 Editor 负载，该读数不代表后续各轮负载。以下记录目标 Editor 内正式核心的绝对耗时与输出，旧核心未获得有效同输入基线。

独立核心采样通过官方 Unity CLI 的 `eval_file` 创建 World，调用 `LifeWorld`、`LifeSimulationSystem` 与 `LifeRasterJob`。Stopwatch 只包住实际操作，CLI 分发、动态编译、输入准备与初始建树另记。每个版本测量五次冷请求及其热重放，冷、热交替；不同版本顺序采样，没有交替安排版本，不报告精确加速倍数。连续八宏步面对同一次运行中的不同状态，不算八次重复测量。真实 Play 的被动观测单独记录。

多次检查发现目标 Editor 的 Profiler 历史录制开启，并出现内存压力与丢弃历史帧警告。耗时保留为各次 Editor 条件下的诊断和输出证据，不作为纯游戏性能上限。每次关闭历史后的真实 Play 单独注明；仅先前关过录制，不能证明随后重进 Play 的采样仍关闭。不同演化状态不能作精确性能对照。

批量建树前的数据在 [core.json](../../Tools/Benchmarks/Results/core.json)、[metapixel.json](../../Tools/Benchmarks/Results/metapixel.json)、[galaxy.json](../../Tools/Benchmarks/Results/galaxy.json) 与 [scheduler.json](../../Tools/Benchmarks/Results/scheduler.json)，当时的源码和样本哈希见 [source-hashes.json](../../Tools/Benchmarks/Results/source-hashes.json)。这些哈希不代表后续的批量建树和回收优化版本。

分配指标需要更正：本机 `GC.GetAllocatedBytesForCurrentThread()` 对保留的一份 `new byte[1048576]` 前后都返回 0。历史 JSON 保留原始字段，但其中的 `allocatedBytes: 0` 不能证明无分配，不影响单独记录的 Stopwatch 耗时与输出核对。当前工具改用 Unity `GC.Alloc` 的主线程事件计数，并在每轮脚本先执行已知分配和空区间校准。事件样本的 `Value` 是时间指标，不作字节数；缓冲截断时分配结果无效。

## 核心采样

| 输入与实际工作 | 中位数 ms | 五次范围 ms |
| --- | ---: | ---: |

| 256×256、32,429 随机活细胞，连续推进 128 代 | 20.199 | 13.514–21.964 |

| 同一世界，远景 67,108,864 格，生成 1024² 像素 | 1.447 | 1.303–1.553 |

上表为缓存索引与批量归还接入、业务仍与回收互斥时的 [core-memo.json](../../Tools/Benchmarks/Results/core-memo.json)，65 份记录均完成，失败 0。画笔后的正式人口为 1,049,600，五次均在一次 System Update 内完成。随机序列使用种子 `0x12345678`，每次从相同初态连续计算十六次八代，最终人口均为 6,539，没有回退快照。首次 Glider 冷请求记录 1 个初始化分配事件，其余 64 个区间为 0；校准通过，缓冲未截断。历史核心采样与这份采样不是交替对照，未确认混沌、画笔和显示链路加速。

另以 Glider 推进 4096 代并核对人口和五个目标坐标；冷／热输出根与位置相同。稳定结构核对人口不变，混合图案冷／热核对完整规范化根，渲染核对白色像素确实产生。

“热缓存”是重放相同快照和相同跨代请求的复用成本，不能解释为后续混沌演化速度。近景与远景的纹理清理仍固定写入 4 MiB；远景离散波动明显。`Apply` 的 CPU 提交另在 JSON 中记录，不代表 GPU 完成时间。未单独做 CPU Profiler 归因，不据此宣称硬件极限或最优配置。

## OTCA 单元与独立结果核对

输入为 Brice Due 的 [OTCA metapixel RLE](https://copy.sh/life/examples/otcametapixel.rle)：64,691 活细胞，2058×2058，B3/S23。该输入是一个宏单元。本轮推进 35,328 代；多宏细胞的完整输入另见下一节。

每次从初态以 32768、2048、512 代三段推进，总计 35,328 代。五次冷缓存为 529.954–782.934 ms，中位数 548.659 ms；交替重放为 146.853–181.794 ms，中位数 162.506 ms。解析单次 49.374 ms，初始树构造约 49.979–62.128 ms，均不包含在演化时间内。

冷请求触发一次增量回收，峰值已占用节点 262,147，完成后 142,326。演化单批最大 5.953 ms，回收单批最大 2.699 ms，说明约 2 ms 调度预算只能在小批次之间生效，不能承诺每帧严格不超时。十个区间失败 0。

对照使用 [copy/life 原始引擎](https://github.com/copy/life)直接读取相同 RLE 并推进同样代数，不重写参考演化算法。最终人口 64,697，全体坐标按相同 64 位混合函数累计后的和为 `b80862e9e33a47e1`、异或为 `35ed6d6d4e00e5db`，十次与独立参考一致。指纹遍历放在计时与分配区间之外，参考结果见 [metapixel-reference.json](../../Tools/Benchmarks/Results/metapixel-reference.json)。

## 完整 Life-in-Life 输入与正式调度

输入为 Brice Due 的 [metapixel-galaxy.mc](https://copy.sh/life/examples/metapixel-galaxy.mc)，文件注明由 `galaxy.lif` 生成 15×15 个 B3/S23 宏细胞。原文件 122,740 B，通过 [PrepareLifeInLife.py](../../Tools/Benchmarks/PrepareLifeInLife.py) 按 [Golly Macrocell 格式](https://golly.sourceforge.io/Help/formats.html)离线展开为 18,474,689 B 的 RLE。该转换只准备基准输入，运行时的结构导入仍使用既有 RLE 协议。后续回收对照读取素材目录中的同一份 [metapixel-galaxy.rle](../../Assets/StreamingAssets/LifePatterns/metapixel-galaxy.rle)。

解析后有 7,408,195 个活细胞、556,344 个非空位图叶块，范围 30,720×30,720。原文件、转换结果与位图行内容的 SHA256 见 [galaxy-input.json](../../Tools/Benchmarks/Results/galaxy-input.json)。

五次从初态推进 35,328 代的冷缓存耗时为 4191.344–6372.983 ms，中位数 4733.554 ms。最终人口均为 7,070,723，全体坐标指纹和 `f2c01c6befc06876`、异或 `147baceed955b16a` 均与独立引擎一致。五次交替重放的中位数为 0.055 ms，这只证明相同初态和相同请求能够复用，不能当作下一宏代的速度。

十次推进失败 0。冷请求各触发九轮增量回收，峰值节点 1,854,942。演化单批最大 11.725 ms，回收单批最大 48.086 ms。首次解析约 4894 ms，五次初始建树为 5514–9225 ms；这些是逐叶盖章建树版本的记录，大型 RLE 导入当时仍有数秒等待。

当时使用 [MeasureLifeScheduler.cs](../../Tools/Benchmarks/MeasureLifeScheduler.cs) 以相同输入驱动 `LifeSimulationSystem.Update`。准备阶段包含预设建树、盖章、首次回收和 Play 指令处理，随后一次增加 35,328 代待推进量，后续使用零增量时间续跑。这份记录早于当前约两帧的欠账上限，不能直接代表当前自动运行的调度行为。

五次均完成且匹配独立指纹，失败 0。总 CPU 耗时为 4166.786–5833.057 ms，中位数 4774.491 ms，分成 2043–2805 次 System Update。每轮最慢一次 Update 为 2.942–4.765 ms。准备阶段约 5997–6727 ms，不含输入解析。这里的循环没有真实帧等待，也不运行绘制和 UI，因此不是实际 Game 帧率或鼠标延迟测量。

## 批量建树与连续 Life-in-Life

`LifeWorld.BuildShape` 已改为 Burst 中按 Morton 顺序排序叶块，自底向上拼树。相同完整银河的五次建树耗时为 **65.486–150.044 ms，中位数 73.145 ms**；第一次解析单次 3362.125 ms。五次从初态推进 35,328 代的 CPU 耗时为 3794.224–4421.635 ms，中位数 4020.872 ms；十次冷／热输出均与独立指纹一致，失败 0。数据见 [galaxy-bulk-build.json](../../Tools/Benchmarks/Results/galaxy-bulk-build.json)。

这轮峰值已占用节点 262,155，建树结束只保留 3592 个共享节点；旧版峰值还包含逐叶盖章时生成的中间路径。临时输入与排序空间约每叶块 56 字节，556,344 个叶块约 29.7 MiB，建树后释放。新建树会改变根的坐标分区，后续演化的缓存形态也可能变化，不能把所有耗时差异都归到排序本身。

连续核对使用同一个 `LifeWorld`，初态只盖章一次，中间没有重置或回到缓存快照。每个宏步仍按 32768、2048、512 代三段推进；保留初态预设、当前世界和在途引用，按正式阈值执行增量回收。独立 `copy/life` 原始引擎也从相同输入连续推进八步，各检查点比较累计代数、人口及全体世界坐标的和／异或双指纹。

回收与推进交替后重新连续完成 **282,624 代**，初态和八个检查点全部匹配，失败 0；回收未结束时实际执行了 **7488 个推进批次**。峰值已占用节点为 262,408，最终人口 **6,393,451**，指纹和 `c8fbb5e041915d7c`、异或 `2424f6908e5475e4`。指纹存在碰撞可能，未逐个比较两份坐标列表；底层初态在八步后没有恢复，不能视为验证了整个底层周期。参考与当前结果见 [galaxy-eight-reference.json](../../Tools/Benchmarks/Results/galaxy-eight-reference.json)、[galaxy-interleaved-continuity.json](../../Tools/Benchmarks/Results/galaxy-interleaved-continuity.json)。参考从[旧连续记录](../../Tools/Benchmarks/Results/galaxy-continuity-before-memo.json)原先独立计算的预期字段恢复，保留源文件哈希，没有使用优化后的核心生成参考。

当前八个不同宏步的 CPU 耗时约 4.9–10.5 秒，分别面对新的底层状态，不能拿初态重复请求的热缓存成本代替。首次宏步记录 1985 个初始化分配事件，其余七步为 0；校准通过，缓冲未截断。[原互斥版本](../../Tools/Benchmarks/Results/galaxy-continuity.json)为 5.3–9.9 秒，两次没有交替控制外部负载，不作性能改善结论。连续工具每轮交替一批 4096 工作的回收与一批 128 工作的推进，用于核对活跃引用，不等同于正式 System 的时间配额。这些循环不含真实帧等待、UI 和棋盘显示。

## 回收停顿与当前对照

优化前在目标速度为 5120 代每秒的 Play 中被动观测约 20 秒，得到 1939 个样本，原始记录为 [life-frames-before.json](../../Tools/Benchmarks/Results/life-frames-before.json)。其中有 6 段 `IsCollecting` 连续为真，各持续 21 至 23 帧，段内代数不变。这与 System 在整轮回收期间暂停推进的实现一致，说明帧仍在更新时，棋盘也会因等待回收而停在同一代。

观测到的 System 最大耗时为 2.9965 ms，托管 `GC.Collect` 最大为 6.7419 ms，两者是不同机制。采样开头的 1048.9261 ms 间隔没有足够证据归因到核心。旧探针没有记录 `IsRunning`，尾部人手暂停造成的停代数不计作回收停顿。推进、回收与绘制作业的 Recorder 虽然全为 0，但未确认实际收到样本，不能据此宣称作业耗时为零；Profiler 指标与世界状态还可能相差一帧。

以下回收工作量对照保留原阈值和约 2 ms 预算，尚未接入交替调度。提交 `59d7754` 用分支节点的 `CachedExponents` 索引已存在的缓存档位，推进和回收只访问实际条目。提交 `c28307f` 将第三阶段逐个搬运退休 ID 改为 `FreeNodes.AddRange` 批量归还，仍在整轮清扫结束后才复用 ID，回收期间仍暂停推进。两版工作区哈希见[优化前源码](../../Tools/Benchmarks/Results/collection-before-source-hashes.json)和[该阶段源码](../../Tools/Benchmarks/Results/collection-current-source-hashes.json)；System 包含 UI 方的在途欠账上限改动，哈希记录实际参与采样的文件内容。

三份记录各含五次冷请求及五次热重放，均推进完整银河 35,328 代。下表只统计冷请求中的回收 CPU 耗时，输入解析和初始建树不在区间内。

| 版本与原始记录 | 回收总 CPU 中位数 ms | 五次范围 ms | 每次回收批数 / 轮数 |
| --- | ---: | ---: | ---: |
| [优化前](../../Tools/Benchmarks/Results/collection-before.json) | 279.5919 | 239.324–356.726 | 1032 / 8 |
| [仅缓存索引，59d7754](../../Tools/Benchmarks/Results/collection-mask.json) | 200.8816 | 160.492–279.754 | 1032 / 8 |
| [缓存索引与批量归还](../../Tools/Benchmarks/Results/collection-after.json) | 150.0304 | 134.515–182.270 | 607 / 8 |

三组共 30 次输出均匹配独立参考，失败 0。最终人口为 7,070,723，指纹和为 `f2c01c6befc06876`、异或为 `147baceed955b16a`。各版本顺序采样，只能报告这些绝对结果；包含回收的冷请求总 CPU 中位数由 5128.4007 ms 变为 5165.7907 ms，尚未确认整体吞吐提升。

三组分配校准均通过，Recorder 未饱和。首次冷区间分别记录 1、1985、1984 个 `GC.Alloc` 事件，包含首次初始化分配；每组其余九个区间均为 0 事件。这些计数不是字节数，不能把全部区间统称为 0 GC。

[ObserveLifeFrames.cs](../../Tools/Benchmarks/ObserveLifeFrames.cs) 增加 `running`、2 秒预热和 `markerSamples` 后，在原互斥调度中重新采样。完整银河在 5120 目标速度下，从第 14,272 代推进到第 47,072 代，20 秒得到 1817 帧，全部处于运行状态。共 7 段节点回收，每段 **9–13 帧、88.088–152.016 ms**，段内代数不变。因此该阶段的可见停顿仍然存在。两轮面对不同代数和演化状态，不能据此给出精确改善比例。原始数据与各段汇总见 [life-frames-after.json](../../Tools/Benchmarks/Results/life-frames-after.json)、[life-frames-summary.json](../../Tools/Benchmarks/Results/life-frames-summary.json)。

这轮帧间隔中位数 10.4 ms、P99 为 17.2068 ms，System 最大 3.0252 ms，`GC.Collect` 最大 6.7046 ms。另有一次 526.0308 ms 的 Editor 帧间隔，而相邻记录的 PlayerLoop 最大仅 13.2618 ms，缺少证据把这次间隔归到核心。原生作业的聚合零值仍不作独立耗时证据。当前 UI 的分配来源未完成归因，这轮也不能证明整个 Game 路径无分配。

随后检查到目标 Editor 的 Profiler 正持续录制，历史帧范围为 27,882–29,220。停止录制并清空历史后，Unity 已分配内存从 1,946,065,767 B 降到 1,166,049,824 B，减少约 **744 MiB**。目标进程私有内存在两个 OS 快照中为 6842.1 MiB 和 5792.1 MiB，这两个快照与引擎内存计数范围不同。记录及原始警告见 [profiler-memory.json](../../Tools/Benchmarks/Results/profiler-memory.json)。没有操作其他项目或进程，不能据此把先前全部长帧归因到 Profiler。

关闭历史录制后，在同一银河世界的后续状态再次观测 20 秒：第 154,656–180,288 代，1949 帧全部处于运行状态。帧间隔中位数 10.1599 ms、P99 为 13.6553 ms、最大 20.3317 ms；System 最大 3.0126 ms。仍发生 7 段回收停代，各持续 **13–15 帧、119.796–154.899 ms**。这说明回收暂停推进的问题在去掉 Profiler 历史负担后仍存在，不能把清理 Profiler 等同于修复模拟调度。原始记录为 [life-frames-no-history.json](../../Tools/Benchmarks/Results/life-frames-no-history.json)，汇总同在 `life-frames-summary.json`。该区间没有重新校准托管 GC 时间标记，不用其零值证明没有托管回收。

前两次探针只有一帧，未形成有效播放区间，分别保留为[异步超时记录](../../Tools/Benchmarks/Results/life-frames-after-invalid.json)和[无帧推进记录](../../Tools/Benchmarks/Results/life-frames-after-sync-invalid.json)。有效采样临时将 `Application.runInBackground` 从 false 设为 true，采样后已恢复；工具启动后立即返回文件路径，由 Editor 回调写入完成结果，不等待一个占用 CLI 的 Task。

正式 System 当前五次从相同银河初态推进 35,328 代，均匹配独立指纹，失败 0，见 [scheduler-interleaved.json](../../Tools/Benchmarks/Results/scheduler-interleaved.json)。工具以每秒 1,059,840 代和初始 1/30 秒一次提交目标量，之后零时间续跑；这是合成时间参数，不是 Play 速度。CPU 中位数 3415.6273 ms，范围 2951.3383–4234.0511 ms，所有更新中最慢一次 6.8965 ms，软预算仍不能保证严格低于 2 ms。

每轮随后在正式 System 的推进与回收都进行中，提交一条远离原图案的 64 格画笔。五次都在回收未结束时完成，分别耗用 **2、1、1、1、1 次更新**；处理 CPU 中位数 **0.7148 ms**，范围 **0.6838–4.7861 ms**。画笔取消未发布推进、暂停运行，代数保持 35,328；清扫完成后人口由 7,070,723 增到 7,070,787，整个世界双指纹均符合原世界加 64 格的预期。首次画笔有 3 个初始化分配事件，其余四次为 0。此结果不包含鼠标采样、真实帧等待、绘制与 UI，不能称为鼠标到像素延迟。

交替调度后第一份真实 Play 为 [life-frames-interleaved.json](../../Tools/Benchmarks/Results/life-frames-interleaved.json)：1931 帧全程运行，第 11,424–45,792 代，七个完整回收段内各有 3–6 次代数发布，另有一个截断段。采样后检查 Profiler 历史为开启状态，因此不标为关闭历史。记录到一次 456.4727 ms 帧间隔，相邻 System 约 2 ms、PlayerLoop 约 5 ms，未确定间隔原因。

## 重现与范围

- [MeasureLife.cs](../../Tools/Benchmarks/MeasureLife.cs) 记录重复、混沌、混合、画笔与树显示，使用 `unity --json command --project-path <工程绝对路径> --detach eval_file <脚本绝对路径> 600000`，按返回的 jobId 取结果；原始 CLI 响应时间不作性能数据。工具另将完整结果持久化到 `Temp/LifeBenchmarks/<脚本名>-result.json`，避免域重载后只剩失效 jobId。
- [MeasureLifeInLife.cs](../../Tools/Benchmarks/MeasureLifeInLife.cs) 从 UTF-8 的 `Temp/LifeBenchmarks/request.txt` 读取四行：RLE 绝对路径、重复次数、参考指纹和、参考指纹异或。样本放在忽略的 Temp 目录，不污染用户预设目录。单次推进的计时上限 60 秒，未完成会记录失败。
- `MeasureLifeScheduler.cs` 使用相同四行请求格式，以 1/30 秒和 1,059,840 目标速度注入 35,328 代请求，之后零时间续跑，记录正式分帧调度与最终坐标指纹，再在回收和推进同时进行时注入 64 格画笔，完成清扫后核对整个世界；旧 `scheduler.json` 使用早期一秒欠账设置。
- [MeasureLifeContinuity.cs](../../Tools/Benchmarks/MeasureLifeContinuity.cs) 从 `Temp/LifeBenchmarks/continuity-request.txt` 读取两行：RLE 绝对路径、八步独立参考 JSON 绝对路径；只摆放一次，回收与推进交替执行并连续推进八个宏步，每宏步限时 60 秒，记录回收中的实际推进批数。
- [MeasureLifeCatalog.cs](../../Tools/Benchmarks/MeasureLifeCatalog.cs) 读取项目素材目录，调用实际结构库 `Preview` 构造函数，检查人口、预设建树和逐像素结果；完整银河预览采样五次。此工具需要工作区内由 UI 方维护的 `LifePatternLibrary`，界面源文件和提交不属于本轮核心改动。
